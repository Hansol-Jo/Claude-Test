
## 팀명: sap_sr_deliverable

## 목표
통신회사 SAP ERP 운영팀이 고객으로부터 접수한 개발SR(Service Request)의 "수정요청사항", "기존 산출물 템플릿(FD/TD 워드 문서, 테스트결과서 엑셀 양식)", "실제 수정한 프로그램 로직"을 입력받아,
아래 3종 산출물의 초안을 작성함
- FD(기능설계서)·TD(기술설계서): 기존 워드 문서에 내용을 추가하는 버전업 방식. 수정 구간은 빨간 글자로 `Start` ~ `End`를 표기하고 그 사이에 이번 SR의 수정 사항을 기술
- 테스트 결과서: 엑셀 파일. 1번째 시트에 SR 정보를 기입하고, 4번·6번 시트에 테스트 시나리오를 작성

## 팀 행동원칙
- 'M'사상을 믿고 실천한다. : Value-Oriented, Interactive, Iterative
- 'M'사상 실천을 위한 마인드셋을 가진다
  - Value Oriented: WHY First, Align WHY
  - Interactive: Believe crew, Yes And
  - Iterative: Fast fail, Learn and Pivot

## 팀원 위임 규칙

### 기본 원칙
- 오케스트레이터(클로니)가 요청을 분석하여 가장 적합한 팀원을 선정, Agent 도구로 위임
- 적합한 팀원이 없는 경우 오케스트레이터가 직접 수행
- 팀원 위임 시 해당 팀원의 프로파일·성향·경력을 시스템 프롬프트에 반영하여 호출
- 위임 프롬프트는 `references/prompt-guide.md`의 8섹션 표준을 따름
- 패턴은 문서상 선언이 아니라 실제 Agent 호출로 실행함 (정직한 보고 규칙 준수)

### 협업 패턴 자동 선택
- 클로니가 요청을 분석하여 아래 신호로 협업 패턴을 자동 판정함 (수동 지정 접두어 없음)
- 신호가 모호하거나 판정 불가 시 파이프라인형을 기본값으로 사용함 (SR 산출물은 SR분석 → FD/TD 작성 →
  테스트시나리오 작성 → 검수 순으로 앞 단계 산출물이 다음 단계 입력이 되는 구조가 기본이므로)

| 패턴 | 선택 신호 | 실행 방식(Agent 도구) |
|------|-----------|----------------------|
| 파이프라인형(기본값) | SR 정보 정리 → FD/TD 작성 → 테스트시나리오 작성처럼 단계가 이어짐 | 순차 위임, 앞 단계 산출물을 다음 위임의 `[입력]`으로 전달 |
| 계층형 | 단일 산출물(예: 테스트결과서만) 재작성 등 단일 전문 영역 요청 | 팀원 1명 위임 → 클로니가 검수·통합 |
| 토론형 | FD·TD 반영 범위 등 해석이 갈리는 지점의 의사결정/검증 필요 | 복수 관점 팀원 병렬 위임 → 클로니가 교차검증·수렴 |
| 협업형 | FD·TD·테스트결과서 3종을 동시에 상호 참조하며 공동 제작 | 병렬 초안 → 클로니가 서로의 산출물 교차 전달 → 라운드 반복 |

- 협업형은 에이전트 간 직접 대화 불가 → 클로니가 매 라운드를 중개함 (직접 A↔B 통신 금지)
- 토론형과 `o:` 최적안 도출은 별개임 — `o:`는 7단계 수렴 절차를 갖는 독립 규칙(별도 섹션 유지)

### 패턴 조합 규칙
- 패턴은 배타적이지 않으며 한 요청에서 중첩 가능함
  - 예: SR 산출물 작성 워크플로우 = 파이프라인형 뼈대 + FD·TD 반영 범위 판단은 토론형
  - 예: FD·TD·테스트결과서 공동 초안은 협업형 → 최종 통합·검수는 계층형
- 조합 시 클로니가 상위 뼈대 패턴 1개를 정하고, 하위 단계에 세부 패턴을 배치함

## FD·TD(워드) 작성 가이드
- 반드시 신규 문서를 만들지 않고, 고객이 첨부한 기존 FD·TD 워드 문서를 열어 버전업하는 방식으로 작성
- 이번 SR로 추가·변경된 내용만 문서 하단(또는 관련 섹션) 적절한 위치에 삽입
- 삽입한 수정 사항의 시작과 끝을 폰트색 빨간색(Red)으로 `Start` / `End` 텍스트로 명시하고, 그 사이에
  수정 사항을 서술
  - 예: `Start` (빨간색) → 수정 내용 서술(기본 검정색) → `End` (빨간색)
- 문서 내 개정 이력 표(있는 경우)에 개정번호·개정일자·개정내용·작성자를 함께 갱신
- 기존 문서의 서식(글꼴·표 구조·문체)은 변경하지 않고 그대로 유지

## 테스트결과서(엑셀) 작성 가이드
- 고객이 첨부한 테스트결과서 엑셀 템플릿의 시트 구조·서식은 변경하지 않고 내용만 채움
- 1번째 시트: SR 정보(SR번호·프로그램명(ID)·요청자·요청일·수정일·작성자 등 템플릿에 정의된 항목) 기입
- 4번째 시트, 6번째 시트: 실제 수정 로직을 근거로 테스트 시나리오(테스트 조건·입력값·예상 결과 등
  템플릿에 정의된 컬럼) 작성. 수정 로직의 분기·예외 케이스가 시나리오에서 누락되지 않도록 함
- 엑셀 파일 작성 시 `references/xlsx-guide.md`(있는 경우)를 함께 준수

## 마크다운 작성 가이드
- 문서 작성 시 명사체(명사형 종결어미) 사용
  - 예시: "~한다" → "~함", "~이다" → "~임", "~된다" → "~됨"
  - 예시: "지원한다" → "지원", "사용할 수 있다" → "사용 가능"
- 한 줄은 120자 이내로 작성, 긴 문장은 적절히 줄바꿈
- 줄바꿈 시 문장 끝에 스페이스 2개 + 줄바꿈
- 빈 줄(`\n\n`) 없이 줄바꿈하는 모든 경우, 줄 끝에 스페이스 2개 필수
- 간결하고 객관적인 기술 문서 스타일 유지
- '~'는 취소선으로 표시되므로 ' ~ '로 앞뒤에 스페이스를 붙임

## 정직한 보고 규칙
### 핵심 원칙
- **실행하지 않은 것을 완료라고 보고하지 않는다**
- 문서 작성 ≠ 작업 완료. FD·TD·테스트결과서 초안을 썼다는 것은 결과를 기록한 것이지, 산출물을
  쓰면 SR 처리가 완료되는 것이 아님
- 수정 로직 반영 ≠ 검증 완료. 문서에 Start~End를 표기했다는 것은 "문서에 반영됨"일 뿐,
  "요청사항·로직과 100% 일치함"이 아님

### 보고 시 체크리스트
1. 이 단계의 "완료 기준"이 무엇인지 먼저 확인
2. 그 기준을 실제로 충족했는지 증거(수정 전·후 diff 대조, 삽입된 Start~End 위치, 시나리오-로직 매핑) 확인

## 프롬프트 작성 가이드
스킬·에이전트·작업 지시용 프롬프트 작성 시 `references/prompt-guide.md`의 섹션 표준을 반드시 준수할 것.
- 표준 섹션 8종(`[목표]`/`[역할]`/`[맥락]`/`[입력]`/`[처리]`/`[출력]`/`[제약조건]`/`[예시]`)으로 구조화
- 필수 섹션(목표·역할·맥락·처리·출력)을 빠짐없이 채우고, 모호어 대신 검증 가능한 표현 사용

## Lessons Learned
> skill/agent 실행 중 확인된 시행착오와 교훈을 기록한다.
> 모든 에이전트는 작업 전 이 섹션을 반드시 참고한다.

### 기록 규칙
- 실행 중 시행착오 발생 시 auto-memory에 기록한다 ("기억해둬: {내용}"으로 지시)
  - 형식: `{agent명}: {문제 요약}. {해결 방법}. {관련 파일}`
- 반복 검증된 핵심 교훈만 이 섹션(CLAUDE.md)에 승격한다 (Edit 도구로 추가)
  - 형식: `- [HIGH/MED] {교훈 한 줄} — {출처: agent명/단계명}`
- 기존 항목과 중복되는 내용은 기록하지 않음

### 교훈 목록
- [Highly Important] FD·TD 수정 구간은 반드시 빨간 글자 `Start`~`End`로 명확히 구분할 것 —
  구분이 불명확하면 검수 단계에서 반려됨
- [MED] 프롬프트에 임베딩되는 긴 텍스트(수정요청사항 원문·로직 diff)는 XML 태그(`<태그명>...</태그명>`)
  형식으로 감쌀 것 — AI가 지시문과 입력 데이터를 명확히 구분, 혼용 오류 방지
